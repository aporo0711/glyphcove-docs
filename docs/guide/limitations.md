# Known normalisations and limitations

**日本語**: [limitations.ja.md](limitations.ja.md)

- **Only the blocks you edit** go through `mdast-util-to-markdown` normalisation (`_em_`→`*em*`, and so on). Blocks you have not edited are untouched
- **Turning a heading into an ordinary paragraph adds one blank line** after it. The single newline that separated the heading from the next block only kept them apart *because it was a heading*; a paragraph needs a blank line, or the two would be saved as one paragraph and the file would stop matching the screen. Nothing else in the gap changes, and the blocks on either side are still not rewritten
- A paragraph with soft line breaks is expanded to 1 logical line only while it is being edited. Whitespace at a block boundary is preserved as `&#x20;` (it disappears naturally on the next edit)
- A bare URL you type is turned into a link automatically after the sync (remark-gfm's autolink behaviour)
- A pasted table comes in as a table whether it is from Excel, Word or a web page. **Merged cells in Word and web page tables are expanded on paste** (GFM tables have no way to express them. Each value goes into the top-left cell of its merged range, and a notification is shown). **Excel tables alone are still pasted through unchanged** — that is to keep the current behaviour, so merged cells from Excel are not expanded and the columns shift (a known limitation)
- **Tables in a PDF cannot be brought in by pasting.** When you copy a table out of a PDF, the clipboard carries no table structure (usually just the text of each line), and the pasting side has no way to recover the original column positions. If you need a table from a PDF, use **PDF → Markdown conversion** (right-click → "Convert files (Markdown / PDF / Word / Excel / HTML)"). That path reads the ruled lines and the column positions out of the PDF's drawing instructions
- Pasting a ruled-line table handles **only single-line ruled-line pieces and simple ASCII (`+ - |`) grids**. Double lines (`╔═╗`), heavy lines (`┏━┓`), rounded corners (`╭─╮`) and tables with no outer frame are **passed straight through instead of becoming a table**. It makes no guesses about merged cells
- When a ruled-line table **has a different column count on each row, the rows are padded with empty cells to match the widest row** (a table with merged cells converted from Word into Markdown is one such case). **Columns are never dropped, so no value is ever lost**. To put a vertical bar inside a cell, escape it as `\|`, the same as in GFM (a bare `|` is read as a separator)
- A CSV / TSV paste fires **only when the conditions for becoming a table are met** (2 or more rows, the same column count on every row, 2 or more columns; for commas, also 3 or more rows or 3 or more columns). When the format is broken, an unclosed quote for example, **it is not made into a table: the text is pasted as characters** (formatting it into a table on a guess would silently rewrite the original text)
- Pasting a code block from Word is limited by exactly as much as Word has already lost. **2 code blocks that sit next to each other become 1** — Word treats consecutive paragraphs in the same style as one run, and no boundary survives in the clipboard either. **The language (the `js` in ` ```js `) cannot be recovered** (Word only has the typeface. Mermaid / PlantUML diagrams also come back as code blocks with no language after a paste). **A math block that Markdown → Word wrote out comes back as a code block** (math cannot be emitted to Word, so the TeX source is written out as monospaced text). **Code inside a table cell stays body text** (a Markdown table cell cannot hold a code block)
- The preview shows images only from relative paths and `data:` URIs. External `http(s)` images and absolute local paths are shown as a placeholder (the Markdown source is kept as it is)
- ⚠ **Changing an image's width is a drag-only operation.** The corner handles respond only to pointer down → move → up, and there is **no keyboard alternative and no single-pointer alternative (press and release alone)**. This does not meet WCAG 2.2 **2.1.1 "Keyboard" (Level A)**, **2.5.7 "Dragging Movements"** or **2.5.8 "Target Size (Minimum)"** (the handles are 9×9 px against the 24×24 px minimum, and they sit on top of the image itself, so the spacing exception does not apply either). To set a width as a number, press **"Show source"** on the toolbar to open the Markdown beside the preview and edit the `width` in `<img src="..." alt="..." width="480">` by hand (the preview shows that form as a real image, and it is the same form a resize writes out)
- SVG is displayed with `<img>` (scripts inside the SVG do not run). If text disappears in a draw.io SVG, turn on "Convert text to paths" in draw.io's export settings (some browsers do not draw `foreignObject` when the SVG is shown through `<img>`)
- **SVG images in DOCX / XLSX conversion are rasterised to PNG with headless Chrome before being embedded** (Word does not accept an SVG that has no PNG fallback). **draw.io SVGs keep their labels in `foreignObject`, and sanitisation drops those from the SVG being embedded, so in that case they are embedded as PNG** (it looks the same in Word). Where Chrome is not available it warns and falls back to alt text, as before
- DOCX / XLSX conversion reads images **only from local files and `data:` URIs**. External `http(s)` images are not fetched: it warns and falls back to alt text (`IMG003`). Local files are read even outside the workspace, over UNC and through symbolic links (as before. The limit is 10MB per image, 2MB for `data:`)
- ⚠ **MD → PDF conversion: when a document embeds an external `http(s)` image, the local browser that does the printing fetches it and renders it into the PDF** (currently without a warning). The preview and DOCX / XLSX conversion do not fetch. Suppressing the fetch is planned; until then, for documents that must not touch the network, make the images local files before converting to PDF (pasted images are already stored as local files)
- Tables follow GFM (the first row is the header, cells hold inline content, no merged cells). A table you edit has its column-width padding normalised
- The find option "Match whole word" works only on ASCII letters and digits (by the definition of a word boundary, it never matches Japanese). A protected block is treated as 1 match for its whole contents (the whole block is highlighted), and is not a target for replacement
- Ctrl+click (Cmd+click on macOS) on a link opens only `http(s)` / `mailto:` / relative paths under the document's folder / `#heading`. Schemes such as `javascript:` / `file:` / `vscode:` and absolute paths are not opened
- GitHub Alerts become a coloured callout in the preview, in HTML, in PDF and in **Word** (in Word each type gets its own background colour and left rule plus a heading in the document's own language — `Note` / `Important` in an English document, `ノート` / `重要` in a Japanese one — and the `[!NOTE]` marker is replaced by that heading. **Excel writes the body straight into the meta sheet, so there is no callout**). GitHub itself counts a marker as an Alert only when it stands alone on the first line, but this product also treats the one-line form `> [!NOTE] body text` as an Alert (because the preview cannot tell it apart from the two-line form. We put keeping the preview and the conversion result from disagreeing first)
- Mermaid / PlantUML are drawn in the preview, in HTML, in PDF and in **DOCX**. **In Excel, only when `glyphcove.xlsx.mode` is `report`** do they go in as images (the default `data` writes tables only, so it does not draw diagrams either). Where they cannot be drawn (no Chrome, no Java / jar for PlantUML, a syntax error in the diagram) **the code block is emitted as it is and the reason goes into a warning** (`DIA002` / `DIA003`). **All the diagrams in a document are drawn together in 1 pass**, so the browser is not started once per diagram
- A diagram placed in DOCX **is displayed at the size of the diagram itself** (only ones wider than the page are shrunk). The `svg` and `png` settings do not change the display size (all that differs is how clean it looks when enlarged, and the file size)
- In DOCX conversion, the **table of contents is a field**. Right after you open the file in Word it may say `No table of contents entries found`; select the table of contents and press **F9** to expand it (this is how Word works). **Page numbers come out right only in Print Layout view** (in Draft / Web Layout Word does not compute page breaks. The TOC field carries the same `\z` that Word itself uses, and in that case it prints no page numbers)
- In DOCX conversion, a paragraph that holds nothing but an image is **centred** (it is treated as a figure. An image mixed into running text stays in the flow of the line)
- **Only `$$…$$` is treated as math** (the same notation for a block and for inline math in a paragraph).
  **GitHub-compatible `$…$` is not treated as math** — with just 2 `$` on the same line,
  currency like `$100〜$200` or `$HOME` turns into math, and editing then
  rewrites it to `\$100` (measured. The "inline math" ADR in [Architecture and ADRs](../architecture.md)).
  Note that a ` ```math ` code block is not math either (it stays a code block).
  A line break inside inline math is folded into a space (in TeX a line break means the same as a space).
  **In DOCX conversion math is not rendered: the TeX source is written out as monospaced text** (with a warning).
  HTML output for embedding (not standalone) carries no KaTeX CSS, so the layout breaks (with a warning)
- PlantUML runs under the SANDBOX profile for security. **Pulling in local files or URLs with `!include` cannot be used** (the standard library bundled in the jar, `!include <C4/…>` and the like, can be). 1 code block holds 1 diagram (writing 2 or more `@startuml` shows an error)
- Headers/footers in PDF and OCR for scanned PDFs are not supported (every case is stated in a warning). Images in PDF → MD are **raster images only**, and **a diagram drawn as shapes cannot be extracted** (there is no image in the PDF, so it cannot even be detected — a table's ruled lines are expressed with the same drawing instructions, and there is no way to tell them apart)
- Front matter is edited as **raw YAML only** (there is no key/value form UI, because a form breaks YAML comments and key order on the round trip). **Content that cannot be read back as front matter, such as a lone `---` line in the body, is refused on save** (written as it is, the front matter would end there and the rest would turn into headings and the like). If the document is rewritten from outside while you are editing, the edits you had open are discarded
- The dialect is fixed at GFM + YAML Front Matter. Line endings (LF/CRLF) are preserved
