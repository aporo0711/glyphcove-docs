# Conversion (files: "Convert files (Markdown / PDF / Word / Excel / HTML)", folders: "Batch convert files in a folder")

**日本語**: [conversion.ja.md](conversion.ja.md)

| Conversion | Implemented | Notes |
| --- | --- | --- |
| MD → HTML | ✅ | Standalone / folder output, TOC, highlighting, embedded images, sanitization, **the document title** (front matter `title:` / `タイトル:` → the first heading → `Document`, in that order. It is read as YAML, so a wrapped title or a trailing comment is handled correctly, and it comes out as **the same title used for Word / Excel conversion**. If the YAML is broken, a warning is recorded and it falls back to the first heading), **headers/footers when printing** (the same settings and the same format as PDF. **The on-screen appearance does not change; they appear only when the file is printed from a browser**), **Mermaid diagrams** (SVG conversion in advance by default; `glyphcove.html.mermaid` can change it to bundled JS / left as code), **PlantUML diagrams** (SVG conversion in advance by default; `glyphcove.html.plantuml` can change it to left as code. There is no bundled-JS option for PlantUML), **math** (drawn with KaTeX. Standalone output embeds the CSS and the fonts, so the single file can be carried around as it is), **page breaks** (`<!-- pagebreak -->`. Nothing is shown on screen; the page breaks only when printing from a browser and when generating PDF) |
| MD → PDF | ✅ | Headless printing with an installed Edge/Chrome. Paper / orientation / margin settings. **Page headers/footers (running heads)** (settings `glyphcove.pdf.header` / `.footer`; front matter `header:` / `footer:` takes precedence per document. `${title}` `${author}` `${date}` `${page}` `${pages}` are expanded. Page numbers use the CSS `counter()`, so they are actually counted. **Chrome/Edge 131 or later is required**; below that a warning is recorded and nothing is shown). **Watermark** (`confidential: true` in the front matter gives the default wording in the document's own language — `CONFIDENTIAL` in an English document, `社外秘` in a Japanese one — and `watermark: "text"` gives any text you like, slanted and faint behind every page. Text / colour / opacity come from `glyphcove.pdf.watermark.*`. It appears **only on documents that ask for it**). **Mermaid and PlantUML diagrams are always converted to SVG in advance** before printing. **Math is drawn with KaTeX** (it does not depend on JavaScript running in the browser). **Page breaks** (`<!-- pagebreak -->`) |
| PDF → MD | ✅ Lossy | **A tagged PDF (this product's own MD→PDF output, files made by Word/LaTeX, and so on) is restored from its record of the document structure**: heading levels, bullet lists (nesting, numbering), **task-list checkboxes (with or without the ✔)**, block quotes and GitHub Alerts, **bold/italic/strikethrough/inline code**, tables (exactly as the tags record them. **A line break inside a cell becomes `<br>`**), the real alternative text of images. **Superscripts and subscripts in math** (`E = mc^2`. Footnote numbers are not caught up in it). A PDF with no tags goes through text extraction plus inference: heading inference, **multi-column pages are read column by column and put back in order**, **tables are rebuilt as Markdown tables**, **photographs and images are written out to `<output-name>_images/` and inserted at their position in the body**, **links are restored with their URLs from the PDF annotations**, runs of monospaced text become code blocks, `•`/`・` line-leading markers are restored as bullet lists, and words cut at the end of a line are rejoined. Quality report (JSON/MD), page-number comments (tables whose columns could not be determined and images that could not be extracted are reported as warnings) |
| MD → DOCX | ✅ Lossy | Headings/tables/lists/code/images/quotations/footnotes. **Formatting taken from a reference template (.docx)** (`glyphcove.docx.template`), **a table-of-contents field** (headed `Contents` or `目次`, whichever matches the document), **automatic numbering of figures and tables**, headers/footers and page numbers, paper, orientation, and default font. **Code blocks are highlighted with the same colours as the preview and HTML**, links use Word's hyperlink formatting, task lists become `☐`/`☑`, and **GitHub Alerts become coloured callouts**. Images support png/jpg/gif/bmp and data URIs. Math and raw HTML cannot be output, so they are **turned into text with a warning** (`DOC004` / `DOC005`). **Mermaid/PlantUML diagrams and `*.drawio.svg` are embedded as images** (`glyphcove.docx.diagrams` = `svg` (default, vector plus a PNG fallback) / `png` / `off`. Drawing requires Edge or Chrome; without one the code block is kept and a warning is recorded) |
| DOCX → MD | ✅ Lossy | Structure first (mammoth). On top of headings/tables/lists/emphasis, **quotations, inline code, code blocks, and task lists (`☐`/`☑` → `- [ ]`/`- [x]`)** are restored as well. Images are written out to `<output-name>_images/` (no base64 embedding). **Warnings come only from what was actually found in that document** (only when there are tracked changes, comments, headers/footers, Word equations, or embedded objects. **Text inside text boxes is converted**). The **quality report (JSON/MD)** carries the body text of the headers/footers and comments that could not be brought into Markdown (`glyphcove.docxToMd.qualityReport`) |
| MD table → XLSX | ✅ Lossy | One sheet per table. **What is not a table — prose, headings, code, images, diagrams — goes to the meta sheets instead of the grid**, which is what the lossy marker refers to. Sheet-name normalization, formula-injection countermeasures, **cell type inference** (numbers / ISO dates / percentages / currency become real data types; leading zeros, IDs of 16 digits or more, and ambiguous dates are kept as text with a warning), a frozen header row, auto-filter, automatic column widths, and **meta sheets** (`_Metadata` / `_Document` / `_Code` / `_Assets` / `_Diagrams` / `_Warnings`). A line break inside a cell (`<br>`) round-trips as an Excel line break. **`report` mode writes the bold/italic/strikethrough/inline code inside paragraphs, lists, quotations, and footnotes as Excel rich text (per-run fonts)**, so `**` `*` `~~` `` ` `` come back when the file is read into Markdown again (back when it was flattened to plain text, they were lost in the very first generation) |
| HTML → MD | ✅ Lossy | Structure-first. The same engine as pasting from the web: **site chrome (navigation, headers, footers), styles, and scripts are removed** and only the document text is converted (`.html` / `.htm`; a page saved whole does not leak its `<title>` into the body). Tables are rebuilt as GFM tables (**merged cells are expanded** — the value keeps the top-left position and the covered positions become empty cells; **a table nested inside a cell is flattened into that cell's text**; both with warnings), and a table `<caption>` becomes a paragraph just before the table. Body text that looks like a tag (`&lt;application&gt;`) **stays text instead of turning back into a tag**. Images are **neither copied nor embedded** — references are kept as written, and a warning says so when the output lands in a different folder, where relative references no longer resolve. The file is read as UTF-8 (a document declaring another encoding gets a warning) |
| DOCX → HTML | ✅ Lossy | **Direct (never through Markdown)**. Ships the structural HTML the DOCX → MD route already builds along the way, and **keeps merged table cells as colspan/rowspan**. The style mapping for headings/lists/quotes/code/task lists is the same as DOCX → MD. Images are written out to `<output-name>_images/` (no base64 embedding). Underline, text color, fonts, columns, page setup, and other visual details are not preserved. The inventory warnings (tracked changes, comments, headers/footers, Word equations, embedded objects) and the **quality report (JSON/MD, carrying the header/footer and comment text that could not reach the output)** are the same bookkeeping as DOCX → MD |
| XLSX → HTML | ✅ Lossy | **Direct (never through Markdown)**. Writes each sheet as its grid, with **merged cells kept as colspan/rowspan** (exactly what a Markdown hub would drop). Values appear the way Excel displays them (dates, %, `QA-001` and other formats), hyperlinks become real `<a>` links, pictures on the sheets are written out to `<output-name>_images/` (no base64 embedding), hidden sheets carry a marker in their heading, and formulas become their calculated value with a warning. Shapes, charts, pivot tables, cell colors and borders are not converted |
| XLSX → MD | ✅ Lossy | Sheets can be selected. **A merged cell writes its value only in the top-left** (the covered cells are empty), **rows and columns with no values are trimmed from the outside of the table**, **only the table part becomes a table; titles, explanatory text, procedures and the like go into body paragraphs** (separated by blank lines. This product's own MD→XLSX output round-trips with the whole sheet staying as one table), **dates, percentages, currency, and user-defined display formats are output as Excel shows them** (`0.35`→`35%`, `1`→`QA-001`. Dates are ISO), **images on a sheet are written out to `<output-name>_images/`** (no base64 embedding; they are gathered after the table, with their position recorded in the alt text), hyperlinks become `[text](URL)`, and a hidden sheet is converted with a marker appended to its heading (` (hidden sheet)` or `（非表示シート）`, following the language of the workbook). **Bold/italic/strikethrough/monospace applied to only part of a cell is restored as the `**` `*` `~~` `` ` `` markers** (formatting that applies to the whole cell is "how that cell looks", so it is not turned into decoration. That is why the grey italics of a quotation do not turn into `*…*`). Merged cells / formulas / hidden sheets come with warnings. **Quality report (JSON/MD)** (`glyphcove.xlsxToMd.qualityReport`) |

- **Two-stage conversion (via Markdown)**: the X → MD and MD → Y rows above are joined automatically, adding **PDF → Word / Excel / HTML, Word → PDF / Excel, Excel → PDF / Word, and HTML → PDF / Word / Excel** — ten pairs — to the output choices. They appear as "**PDF → Word (via Markdown; layout is not reproduced)**". Exactly as the name says, **what carries over is the document structure that survives the intermediate Markdown; the original layout is not reproduced** (both stages' losses and warnings apply). The result comes with a **quality report that unions both stages' warnings** and opens by saying the conversion ran in two stages (stage 1's own report is embedded in the same file, so what was lost stays readable without keeping the intermediate). **Word → HTML and Excel → HTML are not offered through this route** (the Markdown hub would drop what both ends can express, such as merged cells; the **direct** rows in the table above serve those pairs)
- Batch conversion: multi-selection and recursive folders, overwrite policy (skip / overwrite / numbered rename), settings for parallelism, timeout, and continuing after a failure, cancellation (no broken output is left behind), automatic saving of a JSON log and a human-readable log
- **Merging several Markdown files into one PDF / HTML / Word / Excel**: selecting two or more `.md` files and converting them asks `Merge into one file? ({count} files)` (**the same goes for a folder batch**). The order is the **natural order of the file names** (`2-x.md` → `10-x.md`; a plain character-code sort puts `10` before `2`) and **does not depend on your display language or on your machine's regional settings** — the same files always come out in the same order. The output name is decided in an **input box that defaults to the parent folder name**. **Headings are concatenated as they are**, so each file becomes a chapter as it stands. The seams are **a page break in PDF and Word, and a horizontal rule in HTML** (Excel separates them by sheet). The following are adjusted automatically when merging
  - **Relative image paths are resolved against each file's own location** (`![](img/x.png)` in `a/doc.md` and in `b/doc.md` are treated as different pictures. Naively joining the body text turns one of them into the other's picture. **No base64 embedding**)
  - **Footnotes `[^1]` and reference links `[x]: …` are renumbered per file** (CommonMark takes **only the first** definition of a given name, so the link target in the second file is silently swapped)
  - **In-page links to the same heading** (`[Back](#overview)`) are re-pointed at that file's own heading
  - **Only the front matter of the first file** becomes the document's metadata; **the rest is reported as discarded in a warning** (it is not silently emitted into the body)
  - **The insides of code blocks and inline code are not rewritten** (a document explaining how to write Markdown survives as it is)
  - **In Excel, `report` mode gives "one sheet per file"** (the sheet name is that file's first heading), and **`data` mode puts the document's sequence number in the sheet name** (`1-Sales` `2-Sales`). When tables under the same heading are in more than one file, without the number they become `Sales_2` and you cannot tell where they came from (prefixing the file name was not adopted because it eats up the 31-character limit on sheet names)
  - The conversion log lists **which file each entry came from**
  - Known limitation: **images in a document on a UNC path (`\\server\share\…`) cannot be embedded into Word / Excel when merging** (reported as `IMAGE_UNC_BLOCKED`. PDF / HTML can embed them)
- **Document break**: writing `<!-- md2office: docbreak -->` (`<!-- docbreak -->` also works) makes **Excel's `report` mode split the sheet there** (the merge feature inserts this marker automatically). It is a different marker from a page break (`<!-- pagebreak -->`), and nothing happens in Word, PDF, or HTML
- **Page break**: writing `<!-- pagebreak -->` in the body (`<!-- md2docx: pagebreak -->` / `<!-- md2office: pagebreak -->` are the same) starts a new page there **in DOCX, PDF, and printed HTML**. In HTML it is output as `<div class="ms-page-break"></div>` and **shows nothing on screen** (body-only output with `glyphcove.html.standalone` off carries no styles, so specify `break-after: page` where you embed it. That is reported in a warning). XLSX has no concept of a page break, so it is ignored. **It works in the middle of a line too** (writing `Body text.<!-- pagebreak -->Continued.` splits the paragraph at that position and breaks the page there. Putting it at the end of a paragraph in the preview naturally produces this form). **Inside emphasis or a link** (`**before<!-- pagebreak -->after**`) it also splits at that position, leaving the decoration on both sides. **Inside a heading** it does not split the heading (that would add a fake entry to the table of contents); the break goes just before the heading if the marker is at its start, and just after it otherwise. **A page break is not possible inside a table cell** (a Word cell is a unit that fits on one page). Anything ignored is reported in a warning (`DOC006` / `MD_PAGE_BREAK_IN_TABLE`)
- A scanned PDF (no text layer) is **honestly reported as not converted** (no OCR engine is bundled, so text cannot be read out of an image). **A page with even one character puts that character into the body, however little there is** (a chapter title page, a cover, or a figure-only page has only about ten characters, but the heading is there). A page with fewer than 20 characters is additionally reported with `PDF_SPARSE_PAGE` as "possibly a scan / the images on this page were not extracted"
- **Running heads (headers and footers) repeated on every page, page numbers, and slanted watermarks are kept out of the body** (reported with `PDF_RUNNING_TEXT_SKIPPED`, with a count and examples. They are not removed silently). Mixed into the body they are not merely hard to read: **a PDF this product itself output with running heads or a watermark carries them into every page when read back**, which is why this was added. The decision is **not made from position alone** — a run is removed only when **all** of "it is in the top or bottom margin band of the page", "it is the outermost line on that page", and "text of the same shape appears at the same height and the same alignment on at least a third of the document's pages" hold (something where only the digits change, like a page number, counts as the same shape). **Only one line at the top and one at the bottom are removed**, so a heading immediately below a running head survives. For watermarks, only text that is **slanted (20 to 70 degrees) and at least twice the size of the body** is removed, so vertical labels inside a figure (90 degrees) and figure notes survive
- **A tagged PDF is restored from its record of the document structure** (reported with `PDF_STRUCT_RESTORED`). A tagged PDF records the structure itself — "this range is a heading, a bullet list, a quotation, a table" — and this product's MD→PDF output, Word's PDF output, and most LaTeX papers qualify. Heading levels, bullet lists (including where the marker is drawn as a shape and is not left in the text), **task-list checkboxes (whether the ✔ is there is decided from the drawing operations; where it cannot be told, it falls back to `- [ ]` and is reported with `PDF_CHECKBOX_STATE_UNKNOWN`)**, quotations and GitHub Alerts (from the callout title `ノート` (Japanese: Note) and the like to `> [!NOTE]`), bold/italic/inline code, **strikethrough** (it is in neither the tags nor the text, so the thin rectangles drawn over the characters are picked up from the drawing operations and overlaid. The rule under a heading and the rules of a table have a different height, so they are not caught up in it), tables (**wrapped cells and rule-only tables alike**, exactly as the tags record them. **A line break inside a cell is restored as `<br>`**), and the real alternative text of images are restored. Content the tags do not cover (math and so on) is not discarded either; it is inserted by position. **Vector-drawn figures (Mermaid, PlantUML, draw.io, and so on) are drawn from that region of the page by pdf.js on a headless browser (Edge/Chrome) and written out as PNG** (reported with `PDF_VECTOR_FIGURE_RASTERIZED`. Setting `glyphcove.pdfToMd.vectorFigures`, on by default, and only when `pdfToMd.images` is on). The extent of a figure is derived from the document structure (a `Figure` tag, or the overlap of the figure label's structure tree with the drawing operations), and the text labels inside a figure are part of the image, so they are not output into the body. **Where no browser is available, the output stays as text as before**, and it is honestly reported with `PDF_VECTOR_FIGURE_RASTER_FAILED` / `PDF_VECTOR_FIGURE` (the conversion does not fail). A document whose tags say nothing but "paragraph", and pages whose tags do not reach half the body, are read with the inference below
- **Superscripts and subscripts in math are restored** (with or without tags. `E = mc2` → `E = mc^2`, `xmin` → `x_{min}`). The notation is the same as TeX: one character as it is, two or more wrapped in `{}` (`10^{-7}`). **Footnote and annotation numbers are not caught up in it** — a footnote reference comes out in the same "small and raised" shape, so position and size alone cannot tell them apart. Whether the thing the exponent attaches to is one (a number, a closing bracket, or a variable name of one or two characters), whether the preceding character is not Japanese text, and whether it is not a link are all taken into account (`脚注のある文1です。` (Japanese: "this is sentence 1, which has a footnote") does not become `脚注のある文^1です。`). **Fractions, radicals, integrals, and matrices are out of scope** (the information is not in the PDF; that is the domain of math OCR)
- Heading and paragraph decisions in PDF→MD are made from **statistics over the whole document** (the body's character size, line pitch, and left edge). Even if a single page has extreme content (a figure filled with tiny characters, say), the reading of the other pages does not change
- **Pages of two or more columns are read column by column, finishing the left column before moving on to the next** (reported with `PDF_COLUMNS_REORDERED`). Full-width headings and figure captions are treated as boundaries that separate columns, so a heading comes out before the column it introduces. **Pages where the column boundaries could not be carved out** are left unreordered as before and reported with `PDF_READING_ORDER_SUSPECT` (mistaking a vertical gap inside a figure for a column boundary sends the second half of a paragraph to the end of the page, so only pages where the valley runs the full height of the body are treated as multi-column)
- **Tables are rebuilt as Markdown tables** (reported with `PDF_TABLE_RECONSTRUCTED`). **Where the document draws rules, the cell boundaries are read from those rules** — vertical rules are the column boundaries, horizontal rules the row boundaries. With rules there is nothing to guess, so **a cell wrapped over two lines can still be restored as one cell** (a line break inside a cell becomes `<br>`. It is the same representation as for a tagged PDF, so it stays a line break when converted on to Word / Excel). In software like Word that **places cells vertically centred**, the row number next to a wrapped cell lands **between those two lines**, but since the row boundaries are decided by the rules it is still read correctly as one row. Rules are **drawn as thin rectangles**, so **turning the setting `glyphcove.pdfToMd.images` off means the rules are not read either** (so as not to add a scan of the drawing operations for that alone. The same reason as for restoring bold and italic). A table with no rules is, as before, **inferred from the positions of the characters**: the column boundaries are decided not from the gaps in each row but from **the bands that are vertically empty across the whole table**, so right-aligned numbers whose left edges shift from row to row do not throw the column count off. **To avoid turning a multi-column page into a table, it is checked whether the surrounding lines end at that valley** (that is, whether it is a column boundary for the whole page) before building. A layout whose columns could not be determined is reported with `PDF_TABLE_SUSPECT` as before, and the body is left as plain text. **Even where there are rules, the following are not read from the rules and fall back to estimation from column positions** (falling back honestly is preferred over reading them wrongly): **tables with merged cells** (where the rules stop partway through the grid. Read as a flat table, the content lands in a different column, so **that grid is not used at all**), **tables placed side by side** (because one row spans several tables), **tables with no outer border**, and **pages where the column boundaries could not be carved out**. Fractions in math are out of scope as well
- **Photographs and images are written out as PNG to `<output-name>_images/`** and inserted as `![…](…)` at their original position in the body (reported with `PDF_IMAGES_EXTRACTED`. **They are not embedded as base64**). **Only raster images (photographs, screenshots) can be extracted through this route**. Figures drawn as shapes (Mermaid, PlantUML, diagramming software) do not exist as images in the PDF, but **in a tagged PDF they are made up for by imaging how the page looks** (see "vector-drawn figures" above). The following are not written out: **images smaller than two lines of body text** (icons, bullet markers, the "image not found" symbol. `PDF_IMAGE_TOO_SMALL`), **transparent, invisible images** (often included in PDFs that came from Word), and **images on pages with no text layer** (the whole page is a single photograph, and as PNG it would be tens of MB per page. `PDF_SCAN_IMAGE_SKIPPED`). **An image that does not fit A4 (96 dpi = 1123 × 794 pixels) is shrunk to a size that fits before being written out** (reported with `PDF_IMAGE_RESIZED`. The aspect ratio is kept, and images are never enlarged). The size at which Markdown and browsers display an image is reckoned at 96 dpi, so pixels beyond that go unused in both display and print while only growing the file and the time. To write the original pixels, turn the setting `glyphcove.pdfToMd.imageResize` off. Even then, in documents with many photographs the image folder can end up larger than the original PDF (PNG cannot make photographs as small as JPEG). If you do not need them, turn the setting `glyphcove.pdfToMd.images` off
- **Bold, italic, and strikethrough are restored even in a PDF with no tags** (reported with `PDF_EMPHASIS_FROM_FONT`). A PDF has no record saying "this is bold", so this is **inference from the typeface name and the slant of the characters**. The actual typeface name cannot be obtained from `getTextContent()` (what it returns is only the three of sans-serif / serif / monospace) and **exists only on the drawing side**, so it is read in **the same single scan as image extraction** — **turning the setting `glyphcove.pdfToMd.images` off means the decoration is not restored either** (so as not to add a scan for that alone). **Japanese italics are not an "italic typeface" but a slant of the characters** (the same typeface with a skewed matrix), while Western text uses a dedicated typeface, so both are examined. **Headings and table headers are not marked** (they are already headings by size, and `# **heading**` would be doubled up). Conventions like LaTeX's, where typeface names end in `…TB` (Text Bold) / `…TI` (Text Italic), are supported as well
- **In a PDF with no tags, bullet markers can only be restored where they remain as text**. PDFs made by Word or LaTeX keep `•` / `・`, but **a PDF printed by Chromium (Edge/Chrome) draws the markers as shapes**, so they cannot be restored from the text (a Chromium-printed PDF is tagged, so in practice the structure restoration above recovers the bullet lists)
